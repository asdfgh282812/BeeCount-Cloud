## 2026-08-02 改版补充（群组模型重构）

使用者反馈 2026-08-01 版本的「主帳戶」设计不对：主帳戶不该是一张能自己
刷卡/收款的独立信用卡帳户，而应该是纯管理容器（对应现实中「同一家银行办
好几张卡，银行本身变成主帳户」的场景）。这轮改动详见
[MOZE_FEATURE_GAP_SD.md §2.9](./MOZE_FEATURE_GAP_SD.md#29-信用卡管理整組功能)
和 `CLAUDE.md`，核心变化：新增 `account_type="account_group"`（纯容器，
不能自己被记交易）、`billing-summary` 的应缴金额改成终身跑动余额（溢缴会
正确结转到未来各期）、繳款改成按各子帳户应缴金额分摊、新增到期提醒
（`card_due` 通知）。

**这一轮验证范围 vs 上一轮不同**：这次改动只跑了 backend pytest 全量回归
（`tests/test_credit_card.py` 已重写 + 新增 `tests/test_credit_card_reminders.py`，
全部通过）+ frontend `pnpm build`（含 tsc 类型检查）+ `pnpm test`（73 个
vitest 用例全过，含 i18n key 一致性检查），**没有像上一轮那样再跑一次 Safari
浏览器端到端验证** —— 上一轮的浏览器测试证明了「只跑 pytest 会漏掉纯前端
逻辑 bug」，这次的模型改动同样牵动了不少前端表单逻辑（帳户类型下拉新增
选项、掛靠对象改成只列 account_group、繳款來源帳户排除所有 account_group
等），建议你比照上一轮的方式亲自在浏览器里走一遍，尤其是下面这份清单。

### 建议的手动验证清单（这次没有自动跑，需要你自己确认）

- [ ] **建立主帳户**：帳户页新建帳户，类型选「主帳户(合併帳單)」
      （`account_group`），应该能填信用额度/帳单日/还款日；不应该出现
      「掛靠主帳户」下拉（群組不能掛靠群組）。
- [ ] **建立信用卡子帳户**：新建一张「信用卡」类型帳户，「掛靠主帳户」
      下拉应该只列出上一步建的 account_group（不会列出其它普通信用卡），
      选中后保存成功。
- [ ] **记子帳户交易 + 看合併帳單**：给子帳户记一笔消费，打开主帳户
      （account_group）的帳户详情弹窗，确认「信用卡帳單」卡片正确显示
      本期帳單金額 / 目前應繳 / 可用額度（= 信用额度 - 應繳，新增字段）。
- [ ] **繳款分摊**：如果掛了 2 张以上子卡各自欠不同金额，繳一笔刚好等于
      总应缴的金额，确认交易列表里每张子卡各自出现一笔金额正确的 transfer
      （不是笼统的一笔）；繳款來源帳户下拉不应该出现任何「主帳户」类型
      的帳户（含这个群组自己）。
- [ ] **溢繳**：繳款金额故意超过总应缴，确认多出来的部分变成一笔打在
      「主帳户」自己身上的 transfer（会在交易列表里看到一笔 to 主帳户的
      transfer），且再次查看合併帳單时「目前應繳」变成负数（= 溢缴），
      「可用額度」相应变高。
- [ ] **信用卡繳款入口 + 帳单分期入口**：帳户详情弹窗「信用卡帳單」卡片
      底部应该有「設定自動扣繳」「新增帳單分期」两颗按钮，点击后应该跳去
      对应页面；如果这个主帳户只掛了一张子卡，目标页面的表单应该已经预填
      好帳户（自動扣繳还会预填 monthly_day = 还款日）。
- [ ] **删除保护**：尝试删除一个还有子卡掛靠的主帳户，应该被拒绝并提示
      先解除掛靠。
- [ ] **到期提醒**：这个纯靠时间触发，没法在浏览器里立即看到效果，如果
      想验证可以用 admin 面板手动触发
      `POST /internal/tasks/materialize-recurring`，回传体里应该有
      `card_reminders` 计数字段，然后去通知中心（🔔）确认有没有新通知
      （前提是有帳户的结帳日/到期日刚好命中今天/7 天后/到期当天）。

### 发现并修复的问题（浏览器测试的价值就在这里）

**前端 bug**：`AccountsPanel.tsx` 里「主帳戶(合併帳單)」下拉的过滤条件
一开始写成：

```ts
r.account_type === 'credit_card' &&
  r.id !== form.editingId &&
  r.parent_account_id !== form.editingId
```

**新建**帳戶时 `form.editingId` 是 `null`；这时候
`r.parent_account_id !== form.editingId` 等于 `r.parent_account_id !== null`
——但绝大多数信用卡帳戶本来就没掛靠任何主卡（`parent_account_id` 就是
`null`），这条件会把它们全部误滤掉！结果就是我在浏览器里建「子卡」时，
下拉除了「不掛靠」什么都看不到，「主卡」明明存在却选不到。

单靠 pytest 完全测不出这个 bug——后端校验/写路径的测试用的是直接构造
payload 打 API，不会经过前端这段纯 UI 层的下拉过滤逻辑。这正是"以 web
UI 为主"跑一遍浏览器测试的意义：会在纯后端测试的盲区里抓到真实 bug。

修复：只有在**编辑**模式（`form.editingId` 有值）才排除"自己的子卡"（避免
一步就形成循环），新建模式不做这个排除：

```ts
r.account_type === 'credit_card' &&
  r.id !== form.editingId &&
  (!form.editingId || r.parent_account_id !== form.editingId)
```

修完之后重新走了一遍第 3 步，「主卡」正确出现在下拉里，选中后 API 也
正确落了 `parent_account_id`。

## 二、建议你自己在浏览器里再看一眼的部分

上面端到端流程已经把核心路径走通了，以下是我没顾上测、但值得你自己点
一下确认的边界情况：

- [ ] **编辑已有信用卡时改掛靠**：把一张已经掛靠了主卡的子卡改成掛靠
      另一张主卡，或改成「不掛靠」——`AccountsPanel.tsx` 的 onEdit 回调
      有没有正确把 `row.parent_account_id` 灌回表单（我在代码里加了，
      但编辑路径这次没在浏览器里点过）。
- [ ] **深层循环**：A 掛靠 B、B 掛靠 C，然后想让 C 掛靠 A——服务端
      `_assert_valid_account_parent` 按理会沿着链路一路查下去挡住，
      pytest 只测了最简单的两层循环（A↔B），三层的没写测试用例，你可以
      手动试一次确认报错文案友好（目前是英文 `write validation failed:
      parent account chain forms a cycle`，会经过
      `frontend/apps/web/src/i18n/errors.ts` 的 `localizeError` 兜底，
      没找到对应翻译 key 时**大概率显示原始英文字符串**——如果你介意这
      个文案不够本地化，可以告诉我加一条 i18n key）。
- [ ] **删除有子卡掛靠的主卡**：现有帳戶删除逻辑只挡"有关联交易"的帳戶，
      **没有专门挡"还有子卡掛靠着自己"的主卡**——如果你把主卡删了，子卡
      的 `parent_account_id` 会变成一个查无此帳戶的孤儿引用，
      `billing-summary` 端点这时候查 `account_id` 会直接 404（因为主卡
      本身找不到了），子卡自己单独查合併帳單也会正常（因为它自己没有
      `billing_day` 设定，会回 400 提示未配置）——不是崩溃性 bug，但
      体验上有点突兀，值得你实测一下评估要不要挡。
- [ ] **多帳本场景**：`account` 是 user-global 实体，但
      `billing-summary`/`card-payment` 走的是 `/ledgers/{id}/accounts/...`
      路径，只查该 ledger 底下的交易——如果同一张信用卡在多个帳本都有
      交易记录，合併帳單金额只会算到你当前打开的那个帳本，不会跨帳本
      加总。这是设计上的简化（跟其它 ledger-scoped 读端点一致），但如果
      你有"一张卡横跨多个帳本"的真实使用场景，这点值得注意。
- [ ] **深色/浅色主题切换 + 繁中/简中/英文三语言**：这次只在深色 + 繁中
      下截图确认过，`cardBilling.*`/`cardPayment.*`/
      `accounts.field.parentAccount*` 三语言 key 都写了（简中/繁中/英文
      各一份，`i18n.test.ts` 的 key 一致性测试跑过），但没有切换语言/
      主题实际截图确认排版。
- [ ] **交易列表联动**：帳戶详情彈窗底部的交易列表这次显示"該帳戶下還沒
      有交易"，即便我们已经用 API 建了两笔交易——初步怀疑是这个弹窗的
      交易列表走的是另一条缓存/分页逻辑（不是这次 Phase 4 改动的代码），
      没有深入排查,如果你也看到类似情况请告诉我,我可以另外排查（跟
      billing-summary 无关,那条是直接查 `read_tx_projection`,已经确认
      数字正确）。
